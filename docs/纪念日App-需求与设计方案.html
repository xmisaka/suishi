纪念日

把重要的日子记下来，让一年变得看得见。公历与农历并存，周期与一次性兼收，首页用一枚转动的圆盘，告诉你时间走到了哪里。

01

需求梳理

先把「算什么」定死，再谈「长什么样」

产品定位

一句话：一个纯本地的日子记录器——记录生日、纪念日、忌日、周期性安排与一次性的约定，首页用一枚圆形年盘呈现全年的分布与进度。

与「格物」的关系：同一套工程骨架与设计语言，不同的主题。格物管「东西放在哪」，纪念日管「日子过到哪」。两者共享 Expo 工程结构、五套主题令牌体系、SQLite 存取规范与视觉基调，但数据模型、信息架构、首页核心组件完全独立。

核心概念

整个应用只有一个主实体：一条日子（Event）。所有复杂度都集中在它的两个属性上——用什么历法记、按什么节奏重复。

字段说明取值
name日子名称结婚纪念日 / 妈妈生日 / 交房租
calendar历法solar 公历 · lunar 农历
repeat重复规则once 一次性 · yearly 每年 · monthly 每月 · weekly 每周
anchor锚点日期（原始值）公历存 YYYY-MM-DD；农历存 {年,月,日,闰}。永远保存用户填的原始形态
tone / icon视觉标识一个颜色 + 一个符号，用于圆盘点与列表区分
note备注可空，纯文本
pinned置顶置顶条目在圆盘上略大一圈
notify提前提醒提前 N 天（0 / 1 / 3 / 7 / 30），是否做本地通知待定
deleted_at软删除沿用格物的软删除约定，进回收站可恢复
一个必须先定下来的存储原则。农历条目不能只存换算后的公历日期。农历八月十五对应哪一天，每隔几年就会变一次；只存公历，等于把「农历八月十五」这个事实降级成了某一年的一次快照，明年就错了。所以数据里存的是原始农历值，每年解析出的公历日期是运行时算出来的缓存，不落库。

历法与周期：八种组合的算法约定

「下一次是哪天」这件事，是这类应用里唯一真正会出错的地方。下表把八种组合全部列出，连同边界处理一并定死——这些规则要作为单元测试的用例清单。

组合示例设定「下一次」怎么算边界与处理
公历 · 一次性2027-05-20就是这一天，固定不动已过去则显示「已过去 N 天」
公历 · 每年5 月 20 日今年 5/20；若已过，取明年 5/202 月 29 日：非闰年落到 2/28
公历 · 每月每月 20 日本月 20 日；若已过，取下月 20 日31 日：小月钳到月末（沿用格物 addMonths 的钳制思路）
公历 · 每周每周三本周三；若已过，取下周三跨周边界用本地零点比较，避免时区漂移
农历 · 一次性农历 2026 年八月十五换算成固定公历日锚点存农历原始值，换算结果不落库
农历 · 每年农历八月十五今年农历八月十五对应哪天；若已过，取下一年腊月三十遇小月（该年腊月只有廿九）→ 取廿九；闰月如闰四月 → 非闰年退回四月
农历 · 每月农历每月初一本农历月初一对应哪天用农历月而非公历月推进
农历 · 每周语义不成立——农历不与星期绑定。选择农历时，每周选项置灰不可选。
农历库是这个项目唯一的技术风险点。格物完全没有农历能力，必须新增。两条路：
  ① 引入 lunar-javascript（6tail 的成熟开源库，纯 JS 无原生依赖，覆盖农历、干支、节气、闰月）——推荐，省下的是最容易出错的那部分工作；
  ② 自研 1900–2100 查表法（约 200 行，体积小到可忽略），但大小月、闰月、节气全靠自己写，回归测试成本高。
我倾向 ①：这个库被广泛使用、边界情况经过验证，比自研更可靠。

信息架构

比格物少一个 tab。纪念日的数据量通常在几十条量级，不需要单独的「提醒」页——近期要到的日子直接放在首页圆盘下方。四个 tab + 中央突起按钮，与格物的自定义 TabBar 保持一致。

位置页面职责
1首页圆形年盘（主角）+ 下一个日子的大字倒计时 + 近期三条
2全部列表 / 分组两种视图：按月份、按类型、按历法；搜索与筛选
＋新建（中央突起）单页表单，历法与重复规则用分段控件，日期选择器随历法切换
3日子详情大字倒计时、原始设定、第几次（如「第 3 个结婚纪念日」）、编辑与删除
4我的主题切换、提醒设置、数据备份导出、关于

首页圆盘的功能定义

这是整个应用的核心组件，也是三版方案唯一真正分岔的地方。不论哪一版，它承载的信息是同一套：

元素含义
圆周一年。12 点方向是元旦，顺时针走完 365 天。不滚动、不跨年，永远是「今年」。
弧年度进度——从元旦扫到今天的这一段。
游标今天在圆周上的位置。
圆点每条日子在今年的落点。农历条目用其农历年在今年的换算结果定位。
点色已过去（弱）、30 天内（品牌色，最亮）、更远（中间调）。语义色沿用格物的 sage / amber / clay 三色红线。
圆心当前焦点条目：名称 + 倒计时。三版方案的差异主要在圆心显示什么。
交互拖动旋转圆盘切换焦点条目；点击圆点直接跳到详情。切换时圆心数字滚动、对应圆点放大。
动效清单（三版共用，这是「流畅」的具体指标）。进场时弧从 0 扫到当前进度（800ms，easeOut）；圆点按日期先后依次淡入放大（间隔 40ms，spring）；拖动旋转跟手（gesture-handler + Reanimated，松手带惯性）；切换焦点时倒计时数字纵向滚动（tabular-nums，避免宽度抖动）；圆盘本身有极缓慢的呼吸感（仅方案 B，周期 6s，幅度 2%）。全部动画走 UI 线程，JS 线程不参与逐帧计算。
02

三版设计方案

同一套信息，三种气质

三版的功能完全一致，差异只在视觉语言与圆盘的表现方式。每版给两屏：首页 + 一个次级页。

方案 A

年轮

暖棕纸感 · 与格物同源 · 浅色为主

把「格物」的纸感语言直接延续过来：米白纸底、赭石棕强调、衬线标题。圆盘像一枚安静的年轮——一圈就是一年，今天是一道游标，日子落在环上。圆心显示下一个日子的倒计时。这是三版里最克制、也最不像「又一个工具 App」的一版。

视觉气质安静、纸感、有温度
与格物的延续最高，令牌直接复用
深色表现好，玄夜档现成
实现成本最低
方案 B

天象

墨底暖金 · 深色为主 · 情绪最重

把圆盘当作一面星盘：十二个月是十二道刻度，日子是盘上会亮的光，越近越亮，今天是一颗沉在轨道上的绿点。圆心显示今天的农历日期与干支。整体以深色为默认（浅色系统下降级为墨色卡片），气质接近观星或旧式历书——最适合「纪念日」这个词本身的分量。

视觉气质沉静、有分量、仪式感强
与格物的延续中等，复用玄夜档
深色表现最好，主场
实现成本中等（光晕与呼吸动效）
方案 C

刻度

极简几何 · 中性灰 · 信息密度最高

去掉纸感与装饰，只留一根极细的圆和几段弧。每条日子是一段弧，弧长表示它占用的时间跨度，粗细表示重要程度；圆心显示年度进度百分比。这是三版里最「工具」的一版，也最能一眼看出一年的密度分布——哪些月份拥挤，哪些月份空着。

视觉气质克制、冷静、现代
与格物的延续最低，只共用令牌
深色表现好，中性灰天然适配
实现成本中等（弧段计算与布局）

三版横向对比

维度方案 A · 年轮方案 B · 天象方案 C · 刻度
圆盘读法一圈一年，点是日子十二刻度，点是星光一条条弧，长度即跨度
圆心显示下一个日子倒计时今天的农历与节气年度进度百分比
默认模式浅色（素笺）深色（玄夜）浅色（中性）
一眼看出今天走到哪、下一个是谁节令流转的时间感哪几个月最拥挤
动效重点扫弧 + 点依次亮起呼吸 + 光晕脉冲弧段生长 + 数字滚动
与格物一致性最高中等低
实现成本最低中中
主要风险气质偏安静，不够「纪念」浅色系统下需额外调校偏冷，缺少情绪
我的推荐

方案 A · 年轮。理由是它把「与格物一致」这条要求兑现得最彻底——同一套令牌、同一套视觉语法，两个应用放在一起像一对；实现成本也最低，可以把省下的力气放在真正难的部分：农历换算的边界正确性与拖动旋转的手感。

如果你希望这个应用更有分量、更像一件「纪念」的东西，方案 B 更合适，它的情绪浓度是 A 给不了的，代价是多花的调校时间。

一个折中做法：以 A 的年轮作为骨架，把 C 的「弧长表达跨度」借过来——让每年重复的日子在环上拖出一条极短的弧，表示「这件事会一直持续下去」。这样既不破坏纸感，又补上了 A 信息量偏弱的问题。要不要加，你定。

建议的工程结构

与格物同构，只把业务目录换成纪念日的：lib/db/（events / pref）、lib/lunar/（农历换算与规则解析，纯函数、可单测）、lib/date/（公历计算与格式化）、components/domain/YearDial.tsx（首页圆盘）、lib/theme/（主题运行时）。

把农历与周期规则做成纯函数，是这个项目里最重要的一条工程决定。规则解析不碰数据库、不碰 React、不读系统时间（今天作为参数传入）。这样八种组合的边界情况可以写成一张表逐条断言——2 月 29 日、腊月三十、闰四月、跨年农历日期，全部在测试里锁死。这类逻辑靠手点验证一定会有漏网的。

里程碑建议
